# MySQL 性能与锁范围验证

本地测试日期：2026-11-04（北京时间）。Java 17、Windows 10、20 个逻辑处理器、MySQL 8.0.46、本机隔离实例，Hikari 连接池上限 20。每轮单活动、400 次成功调用；先完成预热。延迟从工作线程实际进入调用开始统计，包含事务与连接池等待，不包含线程池任务排队。

这是调用真实 Spring 事务服务与 MySQL 的进程内负载测试，**不包含 HTTP、TLS、登录与限流开销，不是网站 QPS 或生产 SLA**。每个并发档位仅一次测量，没有置信区间；磁盘、缓存、JIT、后台进程与测量顺序会影响结果。原始结果保留在 [独占锁基线](performance/mysql-exclusive-baseline.json) 和 [共享锁结果](performance/mysql-local.json)。

## 同一热点活动的签到

| 签到锁策略 | 并发 | 成功调用/秒 | P95 ms | 行锁等待次数增量 | 累计等待 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 独占活动锁 | 1 | 153.2 | 12.2 | 0 | 0 |
| 独占活动锁 | 8 | 141.0 | 86.1 | 399 | 18973 |
| 独占活动锁 | 32 | 99.0 | 412.5 | 399 | 74660 |
| 共享活动锁 | 1 | 168.3 | 7.2 | 0 | 0 |
| 共享活动锁 | 8 | 908.3 | 10.9 | 0 | 0 |
| 共享活动锁 | 32 | 2090.7 | 27.3 | 0 | 0 |

锁等待取隔离 MySQL 实例 `Innodb_row_lock_waits`、`Innodb_row_lock_time` 测试前后差值；累计时间可以大于墙钟时间，因为多个事务可同时等待。这不是逐请求 P95 锁等待。

根据结果，将 MySQL 签到读取活动的锁由 `FOR UPDATE` 改成 `FOR SHARE`，随后条件更新自己的报名行。多个不同学生可以同时签到，同一报名仍由行锁和 `status = 'REGISTERED'` 条件保证只转换一次。取消报名、活动取消、轮换码仍先取得活动独占锁，因此不会越过活动取消或码轮换的提交顺序。H2 继续使用独占锁回退，MySQL 分支通过真实库混合并发测试验证。

不直接移除活动锁：如果仅普通读活动再更新报名，活动取消与签到可能读取不同时间的状态，破坏取消后不得签到的规则。共享锁仍可能阻塞管理员取消和更新码，大量签到或异常长事务仍有延迟边界。

## 报名容量的串行化边界

共享签到锁版本同一热点活动报名：

| 并发 | 成功调用/秒 | P95 ms | 行锁等待次数增量 |
| --- | ---: | ---: | ---: |
| 1 | 104.6 | 14.8 | 0 |
| 8 | 142.1 | 69.8 | 399 |
| 32 | 143.7 | 252.2 | 399 |

报名修改活动容量，保留 `FOR UPDATE`。增加并发没有线性提高吞吐，反而增加等待。不要将该策略描述为无边界高并发系统；热点抢票若超出实测能力，需要排队或重新设计名额分配及补偿机制。

## 查询计划

基线模拟数据：2000 用户、20000 活动、50000 报名。共享锁复测复用了这份数据，并保留前轮负载产生的 7 场活动与 2500 条报名；两轮并非严格等量的受控实验，数值只作本地观察。使用 `ANALYZE TABLE` 更新统计信息，再执行 `EXPLAIN ANALYZE`；完整计划写入 JSON。以下为基线数据测量，用于确认访问路径，不是冷缓存性能承诺。

| 查询 | 实际访问路径 | 基线观察 |
| --- | --- | --- |
| 全部活动前 20 条 | `idx_event_starts` 反向扫描 | 读取 20 行，约 0.17 ms |
| TECH 分类前 20 条 | `idx_event_category` 反向索引查询 | 返回 20 行，约 0.16 ms |
| 个人报名前 20 条 | 用户/时间索引 + 活动主键查找 | 返回 20 行，约 0.14 ms |
| 活动名单前 20 条 | `idx_attendees_page` + 用户主键 | 返回 20 行，约 0.60 ms |
| `%199%` 包含搜索 | 按时间索引扫描后过滤 | 扫描 4326 行得到前 20 条，约 11.5 ms |
| `%199%` 搜索计数 | 全表扫描 | 扫描 20000 行，约 12 ms |

空搜索不再附加恒真的 `LIKE '%%'`，分类使用直接等值谓词；名单新增 `(event_id, registered_at, id)` 索引，报名列表稳定使用时间和 id 排序。`LIKE '%关键词%'` 仍不能靠普通 B-tree 实现任意子串索引，计数会扫描全表；规模更大时需评估全文索引、前缀检索或搜索服务，当前不宣称已解决。offset 深分页和精确 COUNT 同样保留成本。

## 复现

只允许对**可丢弃、名称以 `_test` 结尾的独立 MySQL 数据库**运行。测试会清空其中业务表；不复用生产库。服务只需普通测试库权限及读取 InnoDB 全局状态权限。

```powershell
$env:RUN_PERF = 'true'
$env:TEST_DB_URL = 'jdbc:mysql://127.0.0.1:3308/campusflow_test?serverTimezone=Asia/Shanghai&rewriteBatchedStatements=true'
$env:TEST_DB_USERNAME = '你的测试用户'
$env:TEST_DB_PASSWORD = '你的测试密码'
mvn '-Dtest=PerformanceMeasurementTest' '-DargLine=-Duser.timezone=UTC' test
```

默认集成测试不会执行该负载测试。`PERF_REUSE=true` 仅用于同一次隔离实验复用已验证的固定模拟数据，避免重复造数；正式比较需控制样本、预热、测试顺序并增加重复轮次。独占锁基线是在本次开发中间版本测得；当前脚本执行共享锁。要比较独占锁，需在独立副本中把 `checkIn()` 的活动锁改回 `FOR UPDATE`，其余业务逻辑保持一致，并重新初始化同量数据。
